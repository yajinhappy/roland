Part 6

정산

대금이 지사로 직접 들어가는 구조 · 법인별 세무 분리 · 매일 새벽 돌아가는 대사 엔진.

직정산 구조

결제 허브는 돈을 만지지 않는다. 데이터의 중계와 모니터링만 하고, 자금은 PG에서 지사 계좌로 간다. 이 원칙이 깨지는 순간 본사에 해외 매출이 계상되고 이전가격 이슈가 따라 붙는다.

주체쥐는 것쥐지 않는 것
본사 HQPG 계약 · MID 발급 · Secret Key · 라우팅 정책 · 통합 모니터링대금 · 매출 계상 · 세무 신고
지사 법인정산 계좌 · 매출 인식 · 법정 인보이스 · 현지 세무 신고 · ERPPG 협상 · 인증키 · 라우팅 룰
결제 허브세션 · 라우팅 · 세액 계산 · 배송 웹훅 · 원장 기록 · 대사자금 보관 · 자금 이동
정산 주기가 법인마다 다르다는 점

T+1(PayPal) · T+2(토스 · Stripe) · T+3(2C2P) · T+7(MyCard · GASH) · 월 2회(SoftBank). 같은 날 결제된 건이 서로 다른 날 입금되므로 대사는 결제일이 아니라 PG 정산일 기준으로 돌아야 하고, 지사 자금 계획도 MID별 주기를 반영해야 한다. T+7 비중이 높은 대만이 가장 민감.

세무 분리

Tax Engine이 법인 코드로 세율 · 계산 시점 · 증빙 규격을 분기한다. 결제창은 결과만 표시.

  • 세금 포함가 법인은 상품 등록 시 세액이 확정된다. KR · TW · JP · TH. 표시가에서 역산해 순매출과 예수금을 분리.
  • 세전가 법인은 결제창 진입 시 확정된다. US. 유저 거주 주가 정해져야 총액이 나오므로 상품 카드 가격과 결제 총액이 다르다.
  • 법정 증빙은 결제 성공 직후 자동 교부된다. 대만 e-GUI · 태국 e-Tax · 한국 현금영수증은 API 연동. 교부 실패는 결제 실패로 처리하지 않고 재발행 큐로 분리.
  • 청약철회 규정이 국가마다 다르다. 한국 전자상거래법 7일 미사용 환불 · EU 14일 쿨링오프(디지털 콘텐츠 포기 동의 UI 필요). 환불 정책은 법인별 파라미터.
  • 개인정보 보관 요건이 정산 데이터에도 걸린다. EU GDPR 삭제권 · 한국 개인정보보호법 보관기간 분리. 전표의 유저 식별자는 익명화 시점을 별도 정의해야 한다.

원장과 T+1 대사

결제 1건이 곧 분개 1건. 지사별 복식부기 원장에 기록되고, 다음 날 PG 정산 리포트와 대조된다.

분개 예시 — GVC · MyCard · 1,000 TWD

[차변 Debit]
  PG 미수금 (MyCard Clearing Account)        945 TWD
  지급 수수료 (MDR 5.5%)                      55 TWD
                                              ─────────
                                                  1,000 TWD

[대변 Credit]
  게임 매출 (Gravity TW Game Revenue)          952 TWD
  부가가치세 예수금 (TW e-GUI VAT 5%)          48 TWD
                                              ─────────
                                                  1,000 TWD

MDR은 머천트 마스터의 5.5% 적용. 설계서 v1.0 본문 예시는 3.0% 기준이라 수치가 다름 — Part 8 「문서 간 불일치」 참조.

T+1 자동 대사 절차

01
PG 정산 리포트 수집 매일 새벽 각 PG의 Settlement Report를 CSV · API로 자동 수집. 어댑터의 fetchSettlementReport
02
1:1 대조 내부 승인 원장 vs PG 리포트. 트랜잭션 ID · 승인 금액 vs 정산 금액 · MDR 3개 축 검증
03
불일치 분류 Matched · Fee Discrepancy(수수료 차액) · Missing(누락). 1원 · 1센트 단위까지 적발
04
전표 생성 · ERP 전송 일치 건만 entity_id별 회계 전표로 변환 → 지사 ERP(SAP · NetSuite)로 자동 전송
05
원장 잠금 대사 완료 구간은 불변 잠금. 이후 수정은 역분개로만 가능 — 감사 로그 보존
대사가 잡아내지 못하는 구멍

대사는 PG가 보고한 것과 우리가 아는 것을 비교한다. 양쪽에 모두 없는 거래 — 결제창은 열렸으나 세션이 만료되어 원장에 남지 않고 PG에도 승인이 없는 건 — 은 대사 대상이 아니다. 세션 발급 로그와 승인 원장의 대조가 별도로 필요하며 현재 설계에 없다.

Part 7

환불

환불 가능 여부를 결정하는 것은 정책이 아니라 PG의 물리적 제약. 정책은 그 위에 얹힌다.

Capability 제약

대만 MyCard 선불카드 · 편의점 현금 수납 · 일본 Konbini는 온라인 API 취소가 원천 불가능하다. 기술적 제약이므로 운영 정책으로 우회할 수 없고, 결제창 단계에서 처리되어야 한다.

Capability가능불가결제창 처리
온라인 전액 취소토스 · Stripe · PayPal · SoftBank · 2C2PMyCard · GASH · 편의점 현금불가 수단은 사전 고지 팝업 동의 강제
부분 환불토스 · Stripe · PayPal · SoftBankMyCard · GASH · 편의점 · 2C2P 일부부분 환불 대상 상품에서 해당 채널 제외
정기결제 빌링키토스 · Stripe · PayPal · SoftBankMyCard · GASH · 편의점 · 2C2P구독 상품 선택 시 해당 채널 미노출
필터링은 상품 속성과 채널 Capability의 교집합

어드민에서 상품을 「100% 자동 환불 보장」으로 설정하면 환불 불가 채널이 결제창에서 자동 제외된다. 보장 상품이 아니면 노출은 하되 「본 수단은 자동 환불이 불가하며 고객센터를 통한 계좌 환불이 필요합니다」 고지 팝업을 강제한다. 즉 결제 채널 목록은 유저마다 · 상품마다 다르게 렌더링된다.

환불 분기

환불 요청은 두 번 갈린다. 첫 번째는 운영 모드(자동 · CS 검토), 두 번째는 PG Capability(API · 수기).

자동 환불 — 조건 충족 시
  • 조건 미수령 · 미사용 · 7일 이내
  • 1 게임 서버 실시간 검증 — 재화 소모 여부
  • 2 PG 환불 API 자동 호출
  • 3 게임 재화 회수 웹훅 · 원장 역분개
  • 소요 유저 대기 없음
CS 수동 — 운영자 승인 경유
  • 조건 자동 조건 미충족 · CS 검토 모드 설정
  • API 지원 백오피스 원클릭 환불
  • API 미지원 유저 계좌 수기 송금 워크플로우
  • 접수 통장 사본 · 신분증 모달
  • 승인 지사 재무팀 2차 검수 후 송금
재화가 이미 소모된 경우

가챠 소진 후 환불 요청이 가장 흔한 분쟁 유형. 현재 설계는 계정 임시 동결 또는 잔여분 부분 환불로만 규정되어 있고 판단 기준이 없다. 소모율 몇 % 이상이면 거부인지 · 부분 환불 시 회수 대상 재화의 우선순위가 무엇인지가 /revoke 규격과 함께 확정되어야 한다.

Part 8

운영

어드민 8단계 · 오픈 후 실제로 터지는 10가지 · 현재 문서들이 서로 어긋나 있는 지점.

신규 지사 설립부터 일일 마감까지의 실무 순서를 그대로 메뉴 구조로 옮긴 것. Step 1~5는 기반 구축 · Step 6~8은 일상 운영이며, 앞 단계가 비면 뒤 단계가 동작하지 않는다.

엣지케이스 10

서비스 오픈 후 실제로 발생하는 예외. 각각의 방어 아키텍처가 어느 계층에 있는지가 중요하다.

  • 비동기 · 지연 입금 중 상품 만료 — 편의점 · 가상계좌는 입금까지 시차가 있어 그 사이 이벤트가 끝나거나 캐릭터가 삭제될 수 있다. 주문서에 TTL 24시간 부여 · 입금 시점에 상품이 만료됐으면 해당 지사 게임 포인트로 자동 대체 충전.
  • 결제 성공 후 인게임 지급 실패 — 게임 서버 점검 · 네트워크 타임아웃으로 발생하는 Ghost Tx. Saga 보상 트랜잭션으로 재시도 큐(1 · 5 · 15 · 60분) 가동 · 실패 누적 시 CS 수동 지급 큐로 이관. 상태는 PAID_PENDING_DELIVERY로 격리.
  • VPN 환율 차익 우회 결제 — 저환율 국가 웹샵으로 우회해 헐값 대량 결제. 3중 검증 — 접속 IP 국가 · 계정 국가 · 카드 발행국. 불일치 시 차단 또는 글로벌 기준가(USD) 강제 적용.
  • 가챠 소진 후 차지백 — 결제 후 뽑기를 소진하고 카드사에 도난 신고. 차지백 웹훅 수신 즉시 계정 자동 정지 · 약관 동의 이력과 IP 로그를 증빙으로 자동 제출.
  • 미성년자 결제 · 법정 한도 우회 — D2C 비로그인 고액 결제 시도. 1회 · 월 한도 제한 · 일정 금액 초과 시 포털 본인 · 연령 인증(KYC) 강제.
  • 정기 구독 카드 갱신 실패 — 카드 만료 · 한도 초과로 승인 거절. 유예기간 3일 부여 후 혜택 유지 · 매일 1회 재결제 시도 · 카드 갱신 알림 발송.
  • D2C 타인 캐릭터 오입력 — 비로그인 UID 오타로 엉뚱한 캐릭터에 충전. 결제 직전 /verify 호출 결과로 캐릭터 외형 · 레벨 · 직업 확인 팝업 강제.
  • 환율 급변동 · 주문서 불일치 — 주문서 생성과 결제 완료 사이 환율 급변. 주문서 생성 시 환율 15분 스냅샷 동결 · 만료 시 SESSION_EXPIRED 후 새 환율로 세션 재생성.
  • 동일 계정 동시 다중 결제 — 1회 한정 패키지를 멀티 브라우저에서 동시 시도. 결제 시작 시 Redis 분산 락 획득 · 게임 서버 주문 멱등 검증.
  • PG 웹훅 순서 역전 — 환불 웹훅이 승인 웹훅보다 먼저 도착. 상태 머신으로 SUCCESS를 거치지 않은 REFUND 전이를 거부.
방어 계층 분포

10건 중 결제창(프론트) 방어는 3건(3 · 7 · 8), 결제 허브(백엔드) 방어는 5건(1 · 2 · 9 · 10 · 6), 운영 · CS 방어는 2건(4 · 5). 절반이 백엔드 상태 관리에 몰려 있으므로 상태 머신과 멱등 처리의 구현 품질이 전체 안정성을 좌우한다.
