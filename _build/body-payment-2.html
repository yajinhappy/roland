지사 코드

Part 4

결제

두 개의 진입 경로 · 네 개의 상품 유형 · 하나의 결제창. 결제창에 무엇이 보일지는 8단계 필터가 결정한다.

진입 경로

결제창은 하나지만 들어오는 문은 둘. 무엇이 다른가는 인증 여부가 아니라 귀속 법인과 지급 대상을 무엇으로 확정하는가에서 갈린다.

회원 결제창 — 로그인
  • 진입 포털 One-ID · 인게임 클라이언트 웹뷰
  • 지급 대상 세션에 바인딩된 계정 · 그 계정의 캐릭터
  • 법인 확정 선택한 서버의 entity_id
  • 한도 계정 단위 누적 한도 적용 가능
  • 판매 가능 유형 4종 전부
D2C 다이렉트 웹샵 — 비로그인
  • 진입 PC · 모바일 웹 브라우저
  • 지급 대상 서버 + 캐릭터명 → POST /verify
  • 법인 확정 선택한 서버의 entity_id
  • 한도 1회 · 일 한도 강제 — 초과 시 KYC 요구
  • 판매 가능 유형 제한 — 아래 매트릭스

로그인 요구 매트릭스 — 상품 유형이 결정한다

계정 단위 상품은 계정을 알아야 하는데 비로그인은 계정이 없다. /verify 응답의 account_id로 처리하면 타인 계정에 정액제를 걸 수 있게 되고 계정당 1회 제한도 걸 수 없다.

「1회 한정」은 유형과 독립된 별도 축이다. 인게임 아이템이라도 1회 한정이면 D2C에 노출하지 않는다.

D2C가 존재하는 이유

모바일 인앱결제 수수료 30%를 우회하고 지사 직정산 PG(2.1~5.5%)로 결제를 유도하는 공식 웹 채널. 절감분의 일부를 추가 보너스 재화로 유저에게 환원해 웹샵 이동 동기를 만든다. Epic Games Store 도 자체 인게임 결제를 쓰는 개발사는 그 매출을 100% 보유하도록 열어두고 있으며, 2025년 PC 게임 D2C 거래액은 $1B을 넘겼다.

비로그인의 대가

계정 인증이 없으므로 연령 · 법정 한도 · 본인확인이 모두 결제 건 단위로만 통제된다. 누적 결제 추적이 불가능한 경로이므로 금액 상한이 낮게 걸릴 수밖에 없고, 상한을 넘기는 유저는 결국 포털 로그인으로 유도된다 — D2C는 고액 결제 경로가 아니다.

선물하기 — 청구권 귀속

타인 캐릭터 지정이 곧 선물이다. 비로그인 선물은 환불 시 청구인이 결제자인지 수령자인지 다툼이 된다. 결제자 연락처를 필수 수집하고 환불 청구권을 결제자에게 귀속시킨다.

상품 유형

4종. 결제 자체보다 결제 이후에 무엇이 어디에 남는가가 다르고, 그 차이가 배송 대상과 환불 규칙을 결정한다. 「패키지」는 유형이 아니라 구성 방식이다.

복합 묶음을 1차에서 제외하는 이유

포털 캐시도 1차에서 제외

지사를 넘나드는 통합 캐시는 「GV에서 충전 → GVC에서 사용」 시 선수금은 GV · 매출은 GVC가 되어 법인 간 채권채무가 발생하는데 그 정산 규칙이 정해져 있지 않다. 또한 충전 시점에 매출을 잡으면 미사용 잔액이 과대 매출이 되므로 충전 원장과 사용 원장 분리가 선행되어야 하고, 일본 자금결제법의 유료 · 무료 캐시 분리 요건도 얹힌다. 1차는 게임 전용 포인트만 다룬다.

정액제와 구독을 나눈 이유

1회 구매 기간권과 빌링키 자동 결제는 완전히 다르다 — 필요 Capability(빌링키) · 환불 규칙(일할 계산 vs 다음 주기 해지) · 해지 UI 필요 여부가 갈린다. Steam 도 Recurring In-Game Billing 을 별도 규격으로 두고 사용자와 billing agreement 를 따로 체결한다. 묶어두면 GVC · GGT 에서 판매 수단이 없다는 제약이 검토되지 않는다.

지급 대상 확정 캐릭터 상품이면 POST /v1/portal/character/verify → 200 OK. 계정 상품이면 로그인 세션에서 확정
03
세션 발급 · 채널 구성 POST /v1/portal/checkout/sessions → 8단계 필터로 노출 채널 확정. 금액 · 통화 · 법인이 15분 봉인
04
Tax Engine 법인별 세율 · 계산 방식에 따라 세액 분리. GVI만 이 시점에 총액이 확정된다
05
PG 승인 선택 채널의 MID · Secret Key로 승인 요청 → 승인 완료 웹훅을 결제 허브가 수신
06
게임 서버 배송 웹훅 POST /v1/portal/items/deliver — HMAC 서명 · 멱등키. 실패 시 여기서 격리된다
07
회계 분개 지사별 복식부기 원장 기록 → T+1 배치로 지사 ERP 전송

트랜잭션 상태 머신

PG 웹훅은 순서가 뒤바뀌어 도착할 수 있다. 상태 전이를 명시적으로 제한해 승인 없는 환불 · 배송 없는 완료가 성립하지 않게 한다.

채널 노출 필터

결제창의 결제수단 목록은 고정이 아니다. 지사가 켠 것은 후보군이고, 실제 노출은 8단계를 통과한 부분집합이다.

② 「결제수단 없음」을 정식 상태로 정의 — 사유 코드(금액 초과 · 한도 · 수단 없음)와 대안 안내를 표시한다.

「결제수단 없음」은 정상 동작이다

게임 연동 4대 API

규격은 2계층이다 — 규격 정의는 본사(경로 · 필드명 · 서명 헤더 · 멱등 · 재시도), 운영은 지사(게임사 컨택 · 키 발급 · URL 등록 · 검증). 지사는 규격을 바꿀 수 없다.

방향API역할규격 상태
상점 → 포털POST /v1/portal/checkout/sessions결제 세션 발급 · 금액 봉인 · 채널 확정미정의
포털 → 게임POST /v1/portal/character/verify캐릭터 실존 검증 · 계정 매핑정의됨 — 경로 표준화 필요
포털 → 게임POST /v1/portal/items/deliver지급 · 멱등 보장정의됨 — 필드명 · 서명헤더 확정 필요
포털 → 게임POST /v1/portal/items/revoke환불 시 재화 회수미정의

「2대 API」로 알려져 있었으나 실제로는 4개다. 세션 발급은 방향이 반대(상점 → 포털)라 누락되어 있었고, 회수는 환불 워크플로우에만 등장했다.

① 결제 세션 발급 — POST /v1/portal/checkout/sessions

게임 · 웹샵이 결제창을 여는 유일한 경로. 링크가 아니라 API 1콜이다.

// Request   Authorization: Bearer <상점 API 키>
{
  "server_id": "TW_BAPHOMET",
  "character_guid": "CHA_9928174",   // 캐릭터 상품일 때
  "sku_id": "ROO_DIAMOND_1000",
  "quantity": 1,
  "entry_point": "INGAME",           // INGAME · WEBSHOP · PORTAL
  "locale": "zh-TW",
  "return_url": "https://shop.../done"
}
// amount 를 보내지 않는다 — 허브가 SKU 마스터에서 계산한다

// Response — 200 OK
{
  "session_id": "cs_9f21…",
  "checkout_url": "https://pay.gravity.com/c/cs_9f21…",
  "entity_id": "GVC",          // server_id 로 역추적된 값
  "currency": "TWD",
  "amount": 270,
  "tax_amount": 13,
  "bonus_quantity": 100,
  "expires_at": "2026-09-07T11:15:00Z"
}
왜 링크로는 안 되는가

① 금액 위변조 — URL에 금액이 있으면 조작된다. ② 동결 대상 부재 — 금액 · 통화 · 환율 · entity_id를 15분 봉인할 상태가 링크에는 없다. ③ 채널이 동적 — 8단계 필터 결과는 링크 생성 시점에 알 수 없다.

② 캐릭터 검증 — POST /v1/portal/character/verify

결제 전 캐릭터 실존과 계정 매핑을 확인한다. D2C 비로그인 결제의 유일한 신원 확인 수단이라 응답 지연이 곧 이탈이다.

// Request
{ "game_id": "ROO", "server_id": "TW_BAPHOMET",
  "character_name": "艾莉絲_法師" }

// Response — 200 OK · 500ms 미만
{ "status": "SUCCESS", "character_guid": "CHA_9928174",
  "account_id": "ACC_881923", "level": 88,
  "job_class": "High Wizard" }

③ 지급 — POST /v1/portal/items/deliver

결제 완료 시 허브가 호출. X-Gravity-HMAC-SHA256 서명을 포함하고, 동일 order_id는 몇 번 도착해도 1회만 지급되어야 한다.

// Request
{
  "order_id": "ORD-20260907-88219",   // 멱등 키
  "entity_id": "GVC",
  "target": { "type": "CHARACTER",  // CHARACTER · GAME_ACCOUNT · PORTAL_ACCOUNT
               "id": "CHA_9928174" },
  "sku_id": "ROO_DIAMOND_1000",
  "item_code": "ITEM_DIAMOND",
  "quantity": 1000,                // 기본 수량 — 보너스 제외
  "bonus_quantity": 100,            // 웹샵 보너스 — 별도 필드
  "paid_amount": 270,
  "currency": "TWD",
  "timestamp": 1788745200
}

// Response — 200 OK
{ "result": "DELIVERED", "in_game_mail_id": "MAIL_771928",
  "delivered_at": "2026-09-07T11:00:00Z" }

target 을 타입 + 식별자 구조로 둔 것은 유형에 따라 지급 대상이 캐릭터 · 게임 계정 · 포털 계정으로 갈리기 때문이다. 설계서 v1.0은 character_guid 단일 필드였다.

확정 필요 — quantity 의 보너스 포함 여부

설계서 v1.0 예시는 "quantity": 1200 으로 보너스 포함처럼 읽히는데, Step 4 규격은 bonus_quantity 별도 필드라고 한다. 게임 서버가 quantity 만 보고 지급하면 보너스가 누락되거나 이중 지급된다. 위 예시는 분리 방식으로 가정했으나 확정된 규격이 아니다.

④ 회수 — POST /v1/portal/items/revoke

환불 승인 시 재화를 회수한다. 요청 · 응답 규격이 정의되어 있지 않다. 부분 회수 · 잔여 부족 · 계정 동결의 반환 형태가 환불 승인 여부를 좌우하므로 확정이 시급하다.

게임팀 구현 요건 4가지

HTTPS · TLS 1.3 의무 · HMAC 서명 검증 필수 · 멱등키 저장 필수 · /verify 응답 500ms 미만. 어드민 Step 3에서 실제 HTTP 핑과 규격 준수 판정(경로 · 필드명 · 서명 헤더)을 통과해야 등록이 완료된다.

지사가 게임사와 주고받는 것

전달 — Outbound
  • 연동 규격서 — 본사 발행 · 버전 고정
  • HMAC Secret Key — 발급 직후 1회만 평문
  • 샌드박스 환경 · 테스트 계정 · 테스트 캐릭터
  • 웹훅 발신 IP 대역 — 게임사 방화벽 등록용
  • 재시도 정책 · 멱등 규칙
  • 지급 실패 시 CS 에스컬레이션 창구
수령 — Inbound
  • 4대 API URL — 환경별 2세트(sandbox · live)
  • 서버 목록 — server_id ↔ 표시명 ↔ 귀속 법인
  • item_code 목록 및 sku_id 매핑
  • 게임 서버 인바운드 IP allowlist 등록 여부
  • 응답 SLA · 정기 점검 창(시간대)
  • /revoke 지원 범위 — 부분 회수 가능 여부
  • character_guid 포맷 · 기술 담당자 · 에스컬레이션 채널

정기 점검 시간대를 받아두지 않으면 점검 중 배송 실패를 장애로 오판한다.

라우팅과 한도

PG는 전부 동일 인터페이스로 추상화. 신규 PG 추가 시 코어 · 프론트 수정 없이 어댑터만 등록한다.

// 결제 플랫폼 공통 PG 어댑터 표준 인터페이스
export interface IPaymentAdapter {
  readonly providerId: string;      // "STRIPE" · "TOSS" · "MYCARD" · "SOFTBANK"

  createPaymentSession(ctx, req): Promise<PaymentSessionRes>;   // 1. 세션 생성
  verifyAndParseWebhook(ctx, headers, body): Promise<WebhookEvent>; // 2. 웹훅 서명 검증
  capturePayment(ctx, paymentId, amount): Promise<CaptureRes>;  // 3. 승인 · 캡처
  refundPayment(ctx, req): Promise<RefundRes>;                  // 4. 환불 — 지원 시
  fetchSettlementReport(ctx, date): Promise<SettlementItem[]>;  // 5. 대사용 리포트
  registerProduct?(ctx, sku): Promise<RegisterRes>;            // 6. 상품 사전등록 — 요구 PG만
}

6번은 신규 제안이다. 상품 사전등록을 요구하는 PG(MyCard · GASH · 통신사 소액)에서 지사의 이중 등록 작업을 자동화한다 — Part 5 「SKU × PG 동기화」 참조.

한도 4계층 상속

같은 채널이라도 게임마다 최소 · 최대가 달라야 할 수 있다 — 게임별 유저 연령대 · 객단가 · 상품 가격대가 다르기 때문.

계층범위소유성격
1 PG 물리 제약MID × 채널 × 통화본사못 넘음
2 법정 한도법인 × 연령 × 수단지사못 넘음
3 법인 기본법인 × 채널지사기본값
4 게임별 재정의법인 × 게임 × 채널지사필요한 게임만 덮어씀
+ 진입 경로D2C 비로그인지사별도 축
실효 한도 = min(전부) · 재정의는 좁게만

게임별 설정이 법정 한도나 PG 제약을 넘어서 넓힐 수 없다. 막지 않으면 지사 운영자 실수 하나로 법령 위반이 발생한다. 채널 사용 여부도 같은 상속이며 법인에서 끈 채널을 게임에서 켤 수 없다.

Failover는 환불 가능성을 바꾼다

1순위 채널이 죽어 우회했을 때 두 채널의 Capability가 다를 수 있다. GVC는 1~3순위가 모두 온라인 환불 불가이고, GGA는 3순위(편의점 현금)만 불가라 자동 환불 가능 상품이 환불 불가로 바뀐다. Failover 후보는 동일 Capability 등급 안에서만 선정하고, 불가피할 때는 사전 고지 팝업을 다시 띄워 동의를 새로 받는다. 동의 거부 시 처리(결제 중단 · 1순위 복구 대기)는 미확정.

상품 등록 검증이 게임 스코프로 바뀐다

지금은 SKU 등록 시 「법인 통화별 PG 최소 결제 한도 충족」만 본다. 게임별 채널 한도가 생기면 「이 게임에서 이 가격의 상품을 살 수 있는 채널이 하나라도 있는가」를 검증해야 한다. 없으면 그 상품은 등록돼도 아무도 못 산다. Hive 는 이 검증이 없어 범위 이탈 상품이 유저의 결제 시도 시점에 에러로 드러난다.
