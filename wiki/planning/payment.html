결제 설계

지사마다 따로 만들던 결제를, 본사가 하나 만들어 지사들이 가져다 쓴다. 결제 페이지도 하나, 웹샵도 하나, PG 연동도 PG사마다 한 번만 한다. 유저가 낸 돈은 본사를 거치지 않고 각 지사 계좌로 바로 들어간다.

1장

왜 만드나

지금 방식의 문제와 통합 결제로 달라지는 것.

지금과 앞으로

지금은 법인마다 · 게임마다 PG 계약부터 결제창과 게임 연동까지 한 세트를 새로 만든다. 그래서 같은 개발이 반복되고, 결제 기록이 흩어져 전체 매출을 한 번에 볼 수 없고, 게임팀이 나라마다 다른 PG 규격을 직접 공부해야 한다. 본사가 결제 모듈을 하나 만들어 지사들이 나눠 쓰면 이 셋이 해결된다.

무엇이 달라지나

이런 일이 생기면지금앞으로
게임을 새로 런칭한다결제창 · PG 연동을 새로 만든다상품만 등록한다
지사가 새로 결제를 붙인다그 나라 PG를 찾아 처음부터 연동한다계약을 한 번 맺고 등록한다
새로운 PG를 쓰고 싶다쓰려는 지사가 직접 개발한다본사가 한 번 연동하면 모든 지사가 쓴다

돈의 경로는 바뀌지 않는다

유저가 낸 돈은 지금과 똑같이 각 지사 계좌로 바로 들어간다. PG사가 대만 유저에게 받은 돈은 대만 법인 계좌로, 일본 유저에게 받은 돈은 일본 법인 계좌로 간다. 본사가 전 세계 대금을 받아 나눠주면 해외에서 번 돈이 본사 매출로 잡히고 각 나라로 다시 보낼 때 세금 문제가 붙는다.

2장

누가 뭘 하나

본사가 만들어주는 것과 지사가 직접 하는 것.

나누는 기준

본사는 흔들리면 전체가 깨지는 것을 쥐고, 지사는 현지에 있어야 알 수 있는 것을 쥔다. 연동 규격을 지사마다 다르게 정하면 게임마다 붙이는 방식이 갈라져 「한 번만 만든다」는 전제가 무너진다. 반대로 대만 유저가 MyCard를 얼마나 쓰는지, 다이아몬드 1,000개를 대만에서 얼마에 팔아야 하는지는 서울에서 판단할 수 없다.

「정하는 쪽」과 「실행하는 쪽」이 다른 줄은 둘이다 — PG 계약과 연동 규격. PG 계약은 조건은 본사가 협상하고 명의는 지사가 갖는다 — 협상은 몰아서 해야 조건이 좋고, 명의가 지사여야 대금이 지사 계좌로 들어온다. 본사 목록에 「승인」은 없다 — 지사가 가격이나 정산 계좌를 바꿀 때 본사에 결재를 올리지 않고, 승인이 필요한 일은 지사 담당자와 지사 재무팀이 나눠 처리한다.

3장

유저는 어떻게 결제하나

상품을 고르고 아이템을 받기까지, 그리고 게임팀이 만들어야 할 것.

다섯 걸음

유저는 웹샵과 게임 안 상점 두 경로로 들어오지만 결제 페이지는 하나를 쓴다. 게임팀 작업은 2걸음(대상 확인)과 4걸음(지급)에만 걸리고, 환불 회수까지 합쳐 API 셋을 만든다. PG사 규격 · 결제창 · 카드 정보 · 환율 · 세금 · PG 장애 대응은 전부 결제 모듈이 처리한다.

지급 단위 — 계정이냐 캐릭터냐

캐릭터에게 준다계정에게 준다
누가 쓸 수 있나그 캐릭터만계정의 모든 캐릭터
유저가 입력하는 것게임 · 서버 · 캐릭터명게임 · 계정 아이디
확인 화면에 뜨는 것캐릭터명 · 레벨 · 직업계정 아이디 (일부 가림)
주로 이런 상품아이템 · 코스튬 · 패키지게임 포인트 · 이용권 · 구독

지사 관리자가 상품을 등록할 때 정하고 판매를 시작하면 바꿀 수 없다 — 이미 지급된 것의 사용 범위가 나중에 달라지면 유저 자산이 흔들린다. 2걸음에서 남의 캐릭터명을 입력하면 그게 선물이므로 별도 「선물하기」 기능을 만들지 않는다.

로그인이 필요한 상품

상품로그인왜
인게임 아이템 · 코스튬 · 패키지필요 없음캐릭터명 확인만으로 대상이 정해진다
게임 포인트경우에 따라계정 지갑에 들어가므로 계정을 특정해야 한다
이용권 · 구독필요계정 권한을 바꾸는 일이라 본인 확인이 필요하다
계정당 1회 한정 상품필요로그인 없이는 이미 샀는지 확인할 수 없다

로그인 없는 결제에는 금액 상한이 걸린다 — 누적 결제를 추적할 수 없어 법정 한도를 건 단위로만 통제할 수 있다. 상한을 넘기려는 유저는 로그인으로 유도된다.

게임팀이 만드는 API

API누가 부르나무엇을 하나
결제 시작상점 → 결제 모듈결제 페이지를 열어달라고 요청한다. 상품과 대상만 알려주고 금액은 보내지 않는다
대상 확인결제 모듈 → 게임 서버이 계정 · 캐릭터가 있는지 답한다 (2걸음)
지급결제 모듈 → 게임 서버결제가 끝났으니 지급해달라 (4걸음)
회수결제 모듈 → 게임 서버환불이 됐으니 지급한 것을 되돌려달라

첫 줄만 방향이 반대다 — 상점이 결제 모듈을 부른다. 그래서 게임 서버가 만들 것은 아래 셋이다. 상점이 금액을 보내지 않는 이유는 조작을 막기 위해서다 — 11,000원짜리를 1,100원으로 바꿔 보낼 수 있으므로, 상점은 「어떤 상품」인지만 알려주고 금액은 결제 모듈이 등록된 가격표에서 계산한다.

결제는 됐는데 아이템이 안 왔을 때

4걸음에서 게임 서버가 점검 중이거나 네트워크가 끊기면 지급 요청이 실패한다. 돈은 이미 빠져나갔고 아이템은 없는 상태가 되고, 이걸 넷으로 막는다.

  • 실패한 건을 따로 모아둔다. 「결제됐지만 아직 못 준 건」이라는 상태로 표시해 잃어버리지 않게 한다.
  • 자동으로 다시 시도한다. 1분 · 5분 · 15분 · 1시간 간격으로 재시도하고, 게임 서버가 살아나면 그때 지급된다.
  • 같은 요청이 여러 번 가도 한 번만 지급된다. 게임 서버가 주문번호를 기억해 중복을 걸러낸다 — 게임팀 구현에서 가장 중요한 부분이다.
  • 유저에게는 「결제 완료 · 지급 처리 중」으로 안내한다. 「결제 실패」로 표시하면 유저가 다시 결제해 이중 결제가 발생한다. 재시도가 계속 실패하면 고객센터로 넘어가 운영자가 수동 지급한다.
4장

관리자는 뭘 세팅하나

어드민 하나에 본사 권한과 지사 권한이 함께 있다.

어드민 구성

본사용과 지사용을 따로 만들지 않는다. 시스템도 하나, 접속 주소도 하나이고 로그인한 사람에 따라 보이는 화면이 다르다. 지사 계정으로 들어오면 자기 법인 것만 보이므로, 지사가 늘어도 새로 만들 것이 없다. 본사 권한은 결제 모듈 관리와 키 발급 둘뿐이고, 상품 · 가격 · 결제수단 선택 · 금액 한도 · 환불 · 정산 · 매출 조회는 본사 화면에 없으며 본사 승인 절차도 없다.

본사가 발급하는 키

키무엇에 쓰나누가 받아가나
지사별 PG 인증키결제 모듈이 PG사에 승인을 요청할 때 쓴다아무도 — 모듈이 서버에서 직접 꺼내 쓴다
게임별 연동 키결제 모듈과 게임 서버가 주고받는 요청이 위조되지 않았음을 확인할 때 쓴다지사가 받아 게임사에 전달한다

지사는 인증키 원문을 볼 수 없다 — 「우리 법인에 어떤 결제수단이 열려 있고 수수료가 얼마인지」만 조회한다. 본사가 키를 쥐는 이유는 조건을 협상한 쪽이 본사여서, 정산 대사에서 계약한 수수료율이 제대로 적용됐는지 확인해야 하기 때문이다.

지사가 쓰는 화면 여덟

화면하는 일비어 있으면
00 · 결제 준비도아래 항목들의 상태를 모아 「결제가 열리는가」를 판정무엇이 막혔는지 화면을 돌아다니며 찾아야 한다
01 · 법인통화 · 세금 규격 · 대금 받을 계좌를 등록아무것도 시작할 수 없다
02 · 결제수단본사가 열어둔 것 중 쓸 것을 고르고 노출 순서 · 금액 범위를 정함결제수단이 안 보인다
03 · 게임 연동게임과 서버를 등록하고, 본사에서 받은 키로 연결을 확인결제는 되지만 지급이 안 된다
04 · 상품 · 가격무엇을 팔지 정하고 자기 나라 통화로 가격을 매김결제 페이지에 상품이 0개
05 · 결제 모니터링결제가 들어오는 것을 실시간으로 보고, 지급 실패 건을 찾음문제가 생긴 걸 모른다
06 · 환불 · CS환불 접수와 처리, 계좌 송금이 필요한 건은 재무팀 승인환불을 처리할 수 없다
07 · 정산 대사PG가 보낸 정산 내역과 우리 기록을 매일 맞춰봄돈이 제대로 들어왔는지 알 수 없다

기능 메뉴가 아니라 채워야 하는 순서다. 01~04는 처음 한 번 채우고 바뀔 때만 만지고, 05~07은 매일 쓴다. 「결제가 안 열린다」는 대부분 PG나 인증키 문제가 아니라 04의 상품 가격 미입력이므로, 00번 화면이 이를 차단 항목으로 표시한다.

항목정해야 할 것언제까지
