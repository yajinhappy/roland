6선택 상품단건

1건만 선택한다. 복수 상품 선택은 제공하지 않는다.

행썸네일 · 상품명 · 가격 · [✕ 삭제] — 한 행
수량없다 — 항상 1개다. 조절 UI를 두지 않는다
다른 상품 선택기존 선택을 교체하고 「선택한 상품이 바뀌었습니다」로 알린다
금액상품 가격 그대로 — 법인 기본 통화로 표시. 결제창에서 통화를 바꾸면 그때 재계산된다
미선택 시빈 상태 안내 + [결제하기] 비활성
TABLET · MO접힘 바는 상품명 · 금액만 · 삭제는 펼침 시트에서 다룬다
단건 결제 채택 근거
환불여러 건을 한 번에 결제하면 일부만 환불할 때 부분취소를 지원하지 않는 결제수단이 많다 — 간편결제 · 통신사 결제
지급지급은 건 단위로 게임 서버에 요청한다. 3건 중 1건만 실패하면 유저에게 설명할 수 없는 상태가 된다
지급 대상상품마다 캐릭터 지급 · 계정 지급이 다르다. 섞이면 받을 대상을 하나로 정할 수 없다
이용 형태웹샵은 커머스처럼 여러 상품을 모아 배송받는 곳이 아니다 — 하나 골라 바로 지급받는 흐름이다
수량 미적용수량을 허용하면 같은 문제가 되살아난다 — 2개 중 1개만 환불하는 요청이 부분취소에 해당하고, 지급 · 회수도 건별로 나뉜다
복수 구매 시결제를 여러 번 한다 — 주문 하나 = 상품 하나 = 지급 한 번 = 환불 한 번
복수 건 허용 시 선행 확정 사항

나중에 다건을 허용하려면 아래가 함께 정해져야 한다.

1 · 결제 페이지 표시 — 지금 결제창은 「주문 상품」 1행 구조다. 다건이면 목록형으로 바꿔야 한다.
2 · 부분 환불 — 결제수단별 부분취소 지원 여부를 PG마다 확인해야 한다. 안 되는 수단은 전액 취소 후 재결제뿐이다.
3 · 부분 지급 실패 — 「일부만 지급됨」 상태를 새로 정의하고, 모니터링 · 환불 화면에서 건별로 다뤄야 한다.
4 · 지급 단위 혼재 — 캐릭터 지급 상품과 계정 지급 상품을 같은 주문에 담지 못하게 막아야 한다.
5 · 판매 종료 — 결제 도중 일부 상품이 판매 종료되면 그 건만 빼고 진행할지 전체를 막을지 정해야 한다.

4
스크립트 삽입 및 법인 판정
1
호스트 삽입 항목 — 2행
<div id="ro-webshop"></div> <script src="https://shop.gnjoy.com/embed/v1.js" data-target="ro-webshop" data-game="ro_abyss" data-lang="ko"></script>
게임 코드와 언어만 넘긴다. 지사 코드는 넘기지 않는다.
2
법인 판정 — 등록 도메인 기준 지사가 어드민에 자기 도메인을 사전 등록하고, 서버는 요청의 Origin으로 entity_id를 정한다. 프론트가 보낸 값은 신뢰하지 않는다 — 넘겨받으면 다른 지사 가격으로 결제할 수 있다. 미등록 도메인은 로드를 거부한다.
// 등록 예 — 도메인은 지사 하나로만 매핑된다 gnjoy.com → GV KR  KRW ro-abyss.com.tw → GVC TW HK MO  TWD HKD MOP USD ro-abyss.co.id → GGL ID  IDR USD ro-abyss.com → GGH 글로벌  USD EUR
같은 게임을 여러 지사가 서비스해도 도메인이 다르므로 구분된다. 반대로 한 지사가 여러 국가를 운영하는 것은 정상이다 — 대만 법인이 대만 · 홍콩 · 마카오를 함께 서비스한다.
5
렌더 위치 및 오버레이 처리
3
국가 · 통화 — 법인 하위 구분 도메인으로 정해지는 것은 지사까지다. 한 지사가 여러 국가를 운영하므로 통화는 지사당 여러 개다. 접속 국가로 기본값을 정하고, 유저는 지사가 허용한 통화 안에서 바꿀 수 있다.
도메인 → 지사 // 서버가 판정 · 조작 불가 접속 국가 → 표시 통화 // 웹샵은 표시만 · 매칭 없으면 지사 기본값 결제창 → 결제 통화 // 유저가 허용 목록에서 선택
웹샵은 표시만 하고 통화 선택 UI를 두지 않는다. 통합 결제창에서 고른다 — 결제수단이 통화에 따라 달라지므로 같은 화면에서 정한다.
4
본문 — 컨테이너 내 Shadow DOM 렌더 배너 · 메뉴바 · 상품 리스트 · 우측 영역은 #ro-webshop 안에 Shadow Root로 그린다. 호스트 CSS가 침투하지 못하고 웹샵 CSS도 호스트를 오염시키지 않는다.
5
오버레이 — body 직속 별도 레이어 렌더 MO 바텀시트 · 상품 전면 모달 · 대상 변경 딤 알림은 컨테이너 안에 두면 임베드 영역 안에서만 덮여 잘린다. 그래서 document.body 직속에 별도 오버레이 레이어를 만들어 거기에 그린다. 이 레이어도 Shadow DOM으로 격리한다.
body ├─ 호스트 GNB ├─ #ro-webshop ← 본문 (Shadow) └─ #ro-webshop-layer ← 시트 · 모달 · 딤 (Shadow)
z-index 기준값을 정해 호스트 GNB보다 위로 올린다.
6
로그인 상태 인계 방식
6
로그인 인계 — 토큰 방식 호스트가 로그인 상태면 초기화 시 토큰을 넘긴다. 웹샵 서버가 검증하면 회원 흐름(B), 토큰이 없으면 비회원 흐름(A)으로 시작한다. 호스트 도메인과 웹샵 도메인이 다르므로 쿠키는 차단될 수 있다 — 그래서 쿠키를 쓰지 않는다.
roWebshop.init({ token: "eyJhbGci…" }) // 로그인 상태 roWebshop.init({}) // 비로그인
7
사후 로그인 — 호스트 통지 A3(비회원 인증 완료) 상태에서 로그인하면 대상이 바뀐다. 호스트가 로그인 직후 setToken()을 호출하면 SDK가 A4 딤 알림을 띄운다.
roWebshop.setToken("eyJhbGci…") // → A4 알림
호스트가 호출하지 않으면 감지할 수 없다. 이때는 결제 요청 시점에 서버가 대조해 해당 시점에 동일 알림을 표시한다 — 무통보 대상 변경은 차단한다.
7
결제 페이지 전환 방식
8
결제창 — 임베드 내 로드 금지 [결제하기]를 누르면 서버에 결제 세션을 만들고, 받은 주소로 화면 전체를 전환한다. 통합 결제 페이지는 웹샵 도메인의 독립 페이지다. 임베드 안에서 PG 결제창을 열면 좁은 영역에 갇히고, 대부분의 PG가 프레임 안 로드를 막는다.
[결제하기] → POST /checkout/sessions // 상품 · 수량 · 대상 (금액 없음) → window.top.location = 결제 페이지 → 결제 완료 → 호스트가 등록한 복귀 URL로 돌아온다
인증키는 서버에만 있다. SDK는 키를 갖지 않는다.
9
버전 관리 — 본사 고정 /embed/v1.js는 v1 계열의 최신을 가리킨다. 지사가 특정 버전을 고정할 수 없게 해 파편화를 막는다. 호환이 깨지는 변경은 v2로만 낸다.
스크립트를 넣을 수 없는 호스트 — 지사 보안정책상 외부 스크립트가 금지되면 iframe 모드를 제공한다. 단 이 경우 바텀시트 · 전면 모달 · 딤 알림이 iframe 안에서만 덮이므로 임베드 높이를 충분히 확보해야 하고, 로그인 인계는 URL 파라미터 토큰으로 받는다. 기본은 SDK 모드이고 iframe은 예외로만 쓴다.
